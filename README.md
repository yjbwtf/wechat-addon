# 微信群助手（DSH 桥接）

把 DeepSeek Harness 接到微信群里，只做**联网搜索问答**、**天气查询**和**群内闲聊/翻旧账**，
并且人设、性格、语气可以随意改。

```
微信群 ──[接入层 wxauto4]──> 桥接服务
                              ├─ 策略层：白名单群 / 只 @ / 限频 / 去重 / 紧急停止
                              ├─ 聚合层：被 @ 后先观察，把连着的几条整合成一次回复
                              ├─ 历史层：SQLite + 读取上限 + 滚动保留 + 到期清理
                              ├─ 人味层：颜文字按权重挂 / 削掉客服腔
                              └─ 大脑层：dsh --profile wechat --json
                                            └─ 人设(persona.yaml) + 工具白名单(只留联网)

设置界面 ui\wechat_ui.exe ──[ui_bridge.py]──> config.yaml / persona.yaml
                                             （ruamel 往返读写，注释一个不丢）
```

## 一、快速开始

```powershell
cd /d C:\wechat_addon

# 0) 打开设置界面（推荐先从这里把配置改完）
.\start.cmd -UI

# 1) 创建环境并安装依赖（首次；虚拟环境会自动建在工作目录之外，见文末说明）
.\start.cmd -Setup

# 2) 列出微信会话，拿到准确的群名，填进 config.yaml 的 whitelist_groups
.\start.cmd -Groups

# 3) 自检：检查配置 + 真实调用一次大脑（会联网）
.\start.cmd -Check

# 4) 控制台演示：完全不接触微信，验证对话链路
.\start.cmd -Demo
#   输入：  摸鱼群|张三|@蓝色大肥鱼 北京今天天气怎么样
#   聚合开着的话，被 @ 后要等静默 6 秒才会真的回复

# 5) 真实监听测试：到群里 @ 机器人发一条，看原始消息能不能收到（只打印不回复）
.\start.cmd -Watch 60

# 6) 正式运行（先保持 config.yaml 里 mode: draft）
.\start.cmd
#   注意：它会**立刻返回**，机器人转入后台运行（pythonw，无窗口）。
#   日志在 data\logs\，或者用 start.cmd -UI 在界面里看。
```

> 也可用 `.\start.ps1`，但本机 PowerShell 执行策略禁止运行脚本，
> 需要 `powershell -ExecutionPolicy Bypass -File .\start.ps1`。
> 推荐直接用 `start.cmd`，不受执行策略限制。
>
> 已验证：自检与演示都能跑通，天气和联网搜索走的是 DSH 账号，
> **不需要额外配置 API Key，也不需要管理员权限**。

## 二、必须先改的两处配置

编辑 `config.yaml`：

```yaml
mode: draft                 # 先用草稿模式，确认稳定后再改 auto

whitelist_groups:           # 必须显式填写，留空 = 不回复任何群
  - "摸鱼群"
  - "家人群"

bot_names:                  # 机器人在群里的昵称（用于识别 @）
  - 蓝色大肥鱼
```

### whitelist_groups 的写法

它是一个 **YAML 列表**。`[]` 表示空列表，也就是「一个群都不回复」。要加群就写成：

```yaml
whitelist_groups:
  - "群名一"
  - "群名二"
```

也可以写成一行（内联形式，效果完全一样）：

```yaml
whitelist_groups: ["群名一", "群名二"]
```

四条规则：

1. **每行前面两个空格，然后一个短横线、一个空格、再写群名。** 缩进多了少了都会解析失败。
2. **群名用英文直引号 `"` 包起来。** 不要用中文引号 `“”`——那是另一个字符，会变成群名的一部分。
   群名里带 emoji、空格、`#`、`:`、`-` 时，引号是必需的，不是可选的。
3. **群名要和微信里显示的完全一致。** 这是精确匹配，多一个空格、少一个 emoji 都会静默失效
   （机器人不会报错，只是永远不回复）。
4. **机器人的昵称也要同步改。** `bot_names` 里写的是它在群里的显示名，用于识别 `@`。
   昵称填错 → 识别不到 @ → 同样静默不回复。

### 不用手抄群名：`-Groups`

精确匹配最容易踩的坑就是群名抄错。用这个命令直接把准确名字打出来：

```powershell
cd /d C:\wechat_addon
.\start.cmd -Groups
```

它会列出微信当前所有会话，并在末尾直接生成一段可以**整段复制粘贴**的配置：

```
whitelist_groups:
  - "摸鱼群"
  - "家人群"
  - "老王"
```

把不想让机器人说话的条目删掉，再覆盖 `config.yaml` 里原来的 `whitelist_groups: []` 即可。

> 注意：执行 `-Groups` 需要微信已登录、窗口未最小化。这一步只是读取会话列表，
> 不会发送任何消息。

## 三、人设 / 性格 / 语气

全部在 `persona.yaml`，**改完立即生效，不用重启**。

```yaml
default:
  name: 小深
  prompt: |
    你是「小深」，一个混在微信群里的 AI 助手。
    性格：热心、机灵，有点嘴贫但不油腻……
    语气：像二十多岁的年轻人，短句，口语化……

groups:
  "摸鱼群":            # 按群覆盖，键名要和 whitelist_groups 一致
    name: 老王
    prompt: |
      你是「老王」，群里最爱抬杠的老哥……
```

`prompt` 会作为「角色设定」注入每次对话。写得越具体（口头禅、句长、禁忌），效果越稳定。

**不可更改的硬约束**写在 DSH profile 里
（`C:\Users\you\.dsh\profiles\wechat\cordis.patch.yml`）：纯文本、不用 Markdown、
不暴露是模型、不编造数字、只允许联网搜索类工具。人设再放飞也突破不了这层。

## 四、草稿确认模式（默认，推荐）

`mode: draft` 时机器人**不会往群里发任何东西**，只把草稿打印出来并存到
`data/drafts/pending.jsonl`：

```
====================================================================
 草稿 #a1b2c3d4   群：摸鱼群   来自：张三
--------------------------------------------------------------------
 对方：@小深 明天天气咋样
 拟回复：明天北京多云，18到27度，出门不用带伞。
====================================================================
 确认发送：python approve.py send a1b2c3d4
 丢弃    ：python approve.py reject a1b2c3d4
```

```powershell
.\.venv\Scripts\python.exe approve.py list        # 看所有待确认草稿
.\.venv\Scripts\python.exe approve.py send a1b2c3d4
.\.venv\Scripts\python.exe approve.py send-all
.\.venv\Scripts\python.exe approve.py stop        # 紧急停止
```

观察一两周，确认回复质量稳定、没有被群友反感，再把 `mode` 改成 `auto`。

## 五、聊天记录：读取上限与滚动保留

```yaml
history:
  retention: weekly      # daily | weekly | forever
  retention_days: 7      # weekly 时生效；daily 固定 1 天
  per_group_max: 500     # 每群最多保存条数，超出淘汰最旧
  purge_interval_min: 30 # 清理任务间隔
  reset_on_expiry: true  # 窗口结束后清空该群记录，重新开始

  read_limit:            # 组装上下文时的读取上限（独立于存储）
    max_messages: 50
    max_chars: 6000
    max_age_days: 3
```

清理任务做三件事：删过期 → 按条数裁剪 → 过期的群重置记录窗口。
想立刻清一次：`.\start.ps1` 之外可执行
`.\.venv\Scripts\python.exe -m src.main --purge-now`。

## 六、安全边界（都写在配置里，不靠自觉）

| 约束 | 配置项 | 默认 |
|---|---|---|
| 只在这些群工作 | `whitelist_groups` | 空（不工作） |
| 只回复 @ 机器人的消息 | `require_at` | true |
| 忽略自己发的消息 | `ignore_self` | true |
| 每群每小时上限 | `rate_limit.per_group_per_hour` | 20 |
| 两条回复最小间隔 | `rate_limit.min_interval_seconds` | 8 秒 |
| 回复前随机延迟 | `rate_limit.reply_delay` | 3~8 秒 |
| 同一条消息只处理一次 | `dedup.window_seconds` | 300 秒 |
| 紧急停止 | `data/STOP` 文件 | 不存在 |

另外发送前有**双重校验**：切换聊天后确认当前窗口群名 == 目标群名，不一致就中止，
防止发错群。

> `data/STOP` 只在**真正启动机器人**时才被清除。跑 `-Setup` / `-Check` /
> `-Groups` / `-Watch` 这些诊断命令不会碰它——诊断顺手解掉急停是错的。
> 想解除急停：桌面上的「急停」快捷方式只负责停止；恢复请直接 `start.cmd`。

## 七、权限要求

**不需要管理员权限。** 当前会话就是在普通用户令牌下跑通的（已验证非提权）。
虚拟环境、依赖、数据、日志全部写在用户目录内。

两条注意：

1. **微信和机器人必须在同一个权限级别。** 如果你手动「以管理员身份运行」了微信，
   非提权的机器人读不到它的窗口（Windows 的 UIPI 会挡住跨级别的 UI Automation）。
   保持两者都普通运行即可。
2. PowerShell 执行策略禁止运行 `.ps1` 是**用户级**设置，提权也解决不了，
   用 `start.cmd` 或 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` 即可。

只有下面这些情况才需要提权：把机器人注册成 Windows 服务或开机自启（用任务计划程序
的「用户登录时运行」可以避免提权）、或者把虚拟环境装到 `Program Files` 这类系统目录。

## 八、风险须知

1. **不要用主号。** 用专门的小号/备用号跑，最坏情况只损失这个号。
2. 微信封号分三档：功能限制（7/30 天，聊天还能用）→ 限制登录（可自助解封）→ 永久封禁。
   永久封禁后聊天记录基本拿不回来，钱包余额可通过官方客服通道提现。
3. **最大的风险是被群友举报**，不是技术检测。所以频率克制、别刷屏、别像广告。
4. wxauto 是第三方 UI 自动化工具，不是腾讯授权软件，使用风险自担。
5. **读取方式是轮询，不是监听。** 官方文档把 `AddListenChat` / `StartListening`
   标为 ✨（付费 Plus 专属）。免费版包里这两个方法存在、调用也不报错，但实测
   **回调永远不触发**（监听线程存活、窗口在前台、群里确实发了消息，回调 0 次）。
   所以本方案只用免费版明确可用的 API 轮询：

   ```
   GetSession() 找未读 → ChatWith() 切窗口 → GetAllMessage() 读消息
   ```

   代价是**会抢占微信窗口焦点**：有未读时立刻切，没未读时每 18 秒也会强制全量读一次。
   跑着机器人的时候基本没法正常用微信，最好用闲置机器或单独的虚拟桌面。
6. **判重用的是微信自带的消息 ID。** `GetAllMessage()` 只返回当前渲染出来的消息，
   同一个窗口会被反复读到相同内容，所以必须按 `msg.id` 去重，不能靠「跳过第一轮」。
   程序启动时会把当前窗口里的消息全部登记为「已见过」（建立基线），只回复之后的新消息。
7. **发送前有双重目标校验**：切窗口后确认当前群名 == 目标群名，不一致就中止，
   防止发错群。
8. **微信主窗口必须保持显示状态，不能最小化、不能收进系统托盘。**
   微信 4.x 只给「正在显示的部分」注册 UIA 控件；窗口一收起来控件树就没了，
   读取会以 `LookupError: Find Control Timeout` 失败。
   所以跑机器人的时候，微信窗口就开着别动（可以放在其他窗口后面，但不能最小化）。

## 九、故障排查

| 现象 | 处理 |
|---|---|
| 找不到 dsh 启动器 | 检查 `config.yaml` 的 `dsh.command` |
| 大脑返回空 | 先跑 `.\start.ps1 -Check` 看报错；确认 DSH 已登录 DeepSeek 账号 |
| 微信窗口读不到消息 | 跑 `.\start.cmd -SelfTest` 核对能否读到白名单群的消息与字段 |
| `-SelfTest` 报"不在会话列表里" | 小号不在那个群里，先用大号把小号拉进去 |
| 一直不回复 | 确认群名在 `whitelist_groups` 里、消息里有 @、且没过频率限制 |
| 回复了历史消息 | 不应发生。程序启动时会建立基线跳过历史，若出现请反馈 |
| 想立刻停机 | `python approve.py stop`，或删掉 `data/STOP` 恢复 |
| 回复带了 Markdown | 发送前已自动清洗；若仍出现，说明人设里没约束住，补一句到 `persona.yaml` |

日志在 `data/logs/bot.log`。

### 为什么虚拟环境不放在 DSH 的工作目录里

实测发现：**当 Python 解释器位于 DSH 工作目录内时，它会被限制成只能写该工作目录**，
写 `%TEMP%`、`C:\Users\you\.dsh\...` 全部返回「拒绝访问」。

后果很直接：`dsh` 每次启动都要把合并后的配置写进
`~/.dsh/profiles/wechat/cordis.yml`，被拒绝后 Node 直接崩溃：

```
Error: EPERM: operation not permitted, open '...\.dsh\profiles\wechat\cordis.yml'
```

原因是工作目录内的 `python.exe` 被授予的沙箱权限项（`S-1-4-...` 前缀）
范围恰好只覆盖工作目录。`C:\wechat_addon\venv` 在工作目录之外，不受此限制。

换位置只需改 `start.cmd` 的 `VENVROOT` 和 `start.ps1` 的 `$venvRoot`，
**但不要把 venv 放回 DSH 的工作目录里面**。

### DSH profile 为什么不在这里

人设的工具白名单和系统提示词写在 DSH 的 profile 里：

```
C:\Users\you\.dsh\profiles\wechat\cordis.patch.yml
```

这个目录归 DSH 自己管：`dsh --profile wechat` 会去 `$DSH_HOME\profiles\wechat`
找它，而 `$DSH_HOME` 同时决定了 DSH 运行时、会话、凭据的位置。
把它整体搬到 F 盘需要连带复制凭据并改 `DSH_HOME`，会让桌面端 DSH 找不到自己的
运行时，风险明显大于收益，所以保持原位。

要改机器人的人设，日常只需要改本目录的 `persona.yaml`（立即生效）；
只有想调整「能做什么 / 输出格式」这类硬约束时才需要动那个 profile 文件。

## 十一、连续消息聚合（回复节奏）

真人聊天不是一问一答的接口调用。群里最常见的节奏是：

```
@蓝色大肥鱼
帮我看看北京明天天气
再顺便说下要不要带伞
```

如果每收到一条就调用一次大脑，机器人会在你还没打完字的时候抢答一句
「在呢在呢」，等真正的问题发出来，它已经说完了——一眼机器人。

开启聚合后（`config.yaml` 的 `aggregate` 段）：

1. 被 @ 的那条消息**不立刻回复**，而是开一个「会话」，同时把**此刻之前**的
   聊天记录快照下来（快照是为了让聚合进来的这几条不会被重复算两遍）；
2. 之后这个群里来的消息继续挂进同一个会话，静默计时器清零；
3. 满足任一条件就认为「对方说完了」，整段整合成**一次**请求：
   - 距最后一条消息 `quiet_seconds` 秒内没有新的（正常情况）
   - 从第一句起已经过了 `max_wait_seconds`（对方一直发个不停）
   - 已经攒够 `max_messages` 条

```yaml
aggregate:
  enabled: true
  quiet_seconds: 6          # 最后一条之后安静多久算「说完了」
  max_wait_seconds: 25      # 最长等待，防止永不回复
  max_messages: 8           # 攒满立刻回，不等静默
  followup_sender: any      # any = 谁说的都算同一段；same = 只算发起 @ 的那个人
  after_reply_window: 120   # 回复后这么久内，接着聊不用再 @（0 = 关）
  after_reply_sender: same  # 窗口内谁算接着聊：same（推荐）/ any
```

### 为什么需要 `after_reply_window`

被 @ 一次之后，对方往往还会再补几句（「nmsl」「那咋了」「你说话啊」）。
如果每句都要求 @，机器人就会突然哑掉 —— 用户看到的是「它不理我了」。
加了这个窗口之后，**刚才触发 @ 的那个人**在 120 秒内再说话就不用再 @。

默认用 `same` 而不是 `any`：19 人的群里如果谁的都算，机器人会变成复读机。

> 这是最早的做法：每群只记一个「最近回复时间」，分不清两个人同时在说话，
> 所以后来升级成了**按人分开的连续对话线程**（见第十四节）。
> 线程打开时用线程；把 `threads.enabled` 关掉才会退回这个窗口。

喂给模型的正文长这样，并明确告诉它「这是同一次发言，只回一条」：

```
—— 张三 说：帮我看看北京明天天气
—— 张三 说：再顺便说下要不要带伞
```

**实测**（`_test_agg.py`，真实调用大脑）：

| 场景 | 结果 |
|---|---|
| 只 @ 不说话 | `干嘛喵~`（不再是「在呢在呢」） |
| @ 后分 4 条说完（天气 + 要不要带伞 + 就这样） | `北京明天多云转阴，11到21度，冷空气来串门儿，可能飘点小阵雨，伞还是塞包里吧喵` —— 一条覆盖全部，带伞那问被整合进去了 |
| 甲 @ → 乙插话 → 甲再说 | `理了理了，这不是冒头了嘛。说啥呀？` |

三个场景共 **3 次**大脑调用 = 一次发言一条回复，没有多余输出。

群内控制指令（`\\stop` / `\\start`）不受聚合影响：收到就立即执行，
并顺手丢弃正在收集的那几条。

## 十二、设置界面（Win11 风格，C 写的）

```
ui\wechat_ui.exe
```

纯 Win32 + GDI + DWM，**不引任何第三方库**，也不依赖 WinUI3 / Windows App SDK。
「Win11 原生观感」靠系统本身的东西：DWM 系统背景材料（Mica）、Win11 圆角窗口、
系统强调色、明暗跟随系统、Segoe UI Variable。编译出来是单文件 exe，拷走就能用。

八个页面：**状态 / 群聊设置 / 消息设置 / 人设与语气 / 权限 / 指令 /
功能性API接入 / 高级**，共 91 个可改项。
顶栏常驻「保存配置 / 放弃修改 / 重新读取」，状态页有「启动机器人 / 停止机器人 /
刷新状态」，还能看实时日志。

> 页面的划分是按**你什么时候会去改它**来的，不是按代码结构：
>
> - **群聊设置**：哪些群、什么时候回（白名单、@、昵称）
> - **消息设置**：怎么回（聚合、连续对话、心情值、分段、节奏、开机补回）
> - **人设与语气**：说话像谁（人味、素材池、提示词、梗词库）
> - **权限**：谁能指挥机器人（指令开关、口令、身份校验、可信会话）
> - **指令**：每条指令自己的开关和触发词（`\agent` / `\截图` / `\开` / `\刷课`）
> - **功能性API接入**：占位，以后放接第三方能力的地方
>
> 「指令」是从「权限」里拆出来的：权限管的是**谁有权**，指令管的是**每条指令本身**。
> 拆开之前，`\截图` 和 `\agent` 那一堆字段挤在权限页里，找一个开关要翻很久。

### 启动 / 停止是怎么判定的

「机器人是否在跑」用两条路一起判，只靠一条都不够：

1. 读 `data/bot.pid`（机器人启动时自己写，正常退出时删），再 `OpenProcess` +
   `GetExitCodeProcess` 确认那个 pid 还活着——这样 pid 文件残留也不会误判成运行中；
2. 兜底扫一遍进程，找 **可执行文件路径在本目录下** 的 `python.exe`。
   pid 文件被删、或者机器人是被别的方式拉起来的，这一步还能认出来。

> 第 2 条只匹配路径以 `C:\wechat_addon\` 开头的 python，
> 所以 DSH 自己那个运行时 python（在 `C:\Users\you\.dsh\` 下）不会被误认。
> 也正因为如此，「运行中」只代表**有个本目录的 python 在跑**，
> 微信链路通不通还得看日志。

**已经在运行时，「启动机器人」会自动变灰**（2 秒刷新一次），防止点出一堆重复进程。
「停止机器人」始终可点——它同时是急停按钮，不该被状态锁住。

点「启动机器人」直接拉起 `venv\Scripts\pythonw.exe -m src.main`（无窗口、脱离界面进程），
然后等最多 12 秒确认 `data/bot.pid` 真的出现了。没出现就提示去看日志区的
`bot.log` / `bot-console.log`，而不是静默失败。

> 早期版本这里写的是「在新的控制台窗口里跑 start.cmd，方便看日志」。
> 那是**错的**：机器人改用 pythonw 起之后，它一个字都不会往控制台写，
> 于是那个窗口永远是个空白黑框，还一直杵到机器人退出为止。

### 那个空的黑框是怎么来的（以及为什么它很难查）

机器人自己是用 `pythonw.exe` 起的（GUI 子系统，**没有控制台**）。
而 Windows 的规则是：**一个没有控制台的进程去起一个控制台程序时，
系统会给那个子进程新建一个控制台窗口**。所以只要代码里还有 `subprocess`
去调 `cmd.exe` / `schtasks` / `powershell` / `taskkill`，屏幕上就会冒黑框。

修法是传 `CREATE_NO_WINDOW`（见 `src/procutil.py` 的 `no_window()`），
已经覆盖的位置：设置界面启动/停止机器人、`stop.py`、`elevate.py` 的 `schtasks`、
`brain.py` 回退到 `dsh.cmd` 的那条路。

**这里有个很容易踩反的细节**，实测记录（`tools/test_nowindow.py` 可以复现）：

| 标志 | 直接子进程 | 子进程再起孙进程 |
|---|---|---|
| 不加 | 弹窗 | 弹窗 |
| `CREATE_NEW_CONSOLE` | 弹窗 | 弹窗 |
| `DETACHED_PROCESS` | **不弹** | **弹**（孙进程新建了控制台） |
| `CREATE_NO_WINDOW` | **不弹** | **不弹** |
| `DETACHED_PROCESS \| CREATE_NO_WINDOW` | 不弹 | 弹（前者优先级更高） |

注意最后一行：`CREATE_NO_WINDOW` 和 `DETACHED_PROCESS` **同时给会被忽略**
（微软文档里写着），所以「两个都加上更保险」是错的 —— 那样等于只有
`DETACHED_PROCESS`。要挡住孙进程，只能用 `CREATE_NO_WINDOW`。

顺带一提，我第一版排查时正是被 `DETACHED_PROCESS` 那一格误导过：
测试里用 `cmd.exe /c ping` 看到「DETACHED 也弹窗」，差一点得出
「DETACHED 没用」的结论 —— 真相是 `cmd.exe` 确实没有控制台了，
**但它起 `ping` 时 `ping` 又新建了一个**。把 `ping` 直接起（不经 `cmd.exe` 包装）
才看出来。所以 `tools/test_nowindow.py` 同时测这两种情况。

### 排查这类问题时，枚举窗口别只认 `ConsoleWindowClass`

`tools/test_nowindow.py` 第一版就是这么写的，结果一个窗口都抓不到 ——
Win11 把 **Windows Terminal 设成默认终端**之后，控制台窗口的类名是
`CASCADIA_HOSTING_WINDOW_CLASS`、宿主进程是 `WindowsTerminal.exe`。
按类名认必然漏。正确做法是认**窗口所属进程是不是控制台宿主**
（`WindowsTerminal.exe` / `OpenConsole.exe` / `conhost.exe`）。

这个测试还刻意保留了「**不加标志时必须能看到窗口**」这条反向断言 ——
否则枚举一旦失效，「加了标志没弹窗」就成了永远成立的空话。
这一条在这次排查里真的救了场：它主动报出「不加标志时也没看到窗口，
所以这个通过没有意义」。

### 运行日志是实时刷新的（不用点「刷新状态」）

日志区每 2 秒自己拉一次，**原地更新**，不重建页面：

- 后端 `/api/live` 只返回「运行状态 + 日志尾巴」，**不读 config.yaml**。
  直接复用 `/api/state` 的话，每 2 秒要展平 80 多个字段，纯浪费。
- 前端只更新状态灯、起停按钮可用性、统计格子和日志框 ——
  **完全不碰输入控件**，所以不可能影响你正在编辑的内容。
- 窗口切到后台就不轮询了；切回前台立刻补一次。
- 你往上翻着看历史时**不会被拽回底部**（只在本来就在底部时跟随）。
- 「运行日志」标题右边有个 `实时 · HH:MM:SS`，否则「它不动」和
  「它已经是最新」看起来一模一样。

**顺带修掉一个会丢数据的 bug**：原来的 `reload()` 是
`VALUES = {...st.values}`，所以点一下「刷新状态」或「重新读取」，
**刚改还没保存的东西就没了，而且没有任何提示**。现在会先把改动记下来，
读回来之后再盖回去。

实测（真浏览器 + CDP）：`liveAt` 从 `14:53:56` 走到 `14:54:02`，期间没点任何按钮，
往 `bot.log` 追加的那行自己出现在日志区里；在「高级」页改一个输入框再点
「重新读取」，值还在、脏标记条也还在。

### 只能有一个实例（以及一个藏得很深的坑）

`Bot.run()` 启动时会先读 `data/bot.pid`：如果里面那个 pid 还活着，就报错退出。

这条不是洁癖。两个实例会各自维护自己的「已读水位」、同时抢微信窗口，
结果是消息被其中一个吞掉、两边都不回复 —— 看起来就是「发了消息它不理我」。

**顺着这条线挖出一个更要命的**：`venv\Scripts\python.exe` 其实是个 **launcher**，
它会再拉起真正的解释器。所以任务管理器里能看到两个 python 进程：

```
20808  C:\wechat_addon\venv\Scripts\python.exe           ← launcher
  └ 5844  C:\...\dsh-runtimes\...\python.exe -m src.main  ← 真正的 Python
```

旧的 `stop.cmd` 按**可执行文件路径**过滤（`$_.Path -like 'C:\wechat_addon\*'`），
只杀得到 launcher，**真正的那个会活下来继续抢微信窗口** —— 急停形同虚设。

现在杀进程的逻辑全部集中在 `stop.py`，三路一起匹配，命中任一路就结束：
`data/bot.pid` 里的 pid、可执行文件路径在本目录下的 python、
以及命令行含 `-m src.main` 的 python。换任何解释器起的实例都能收掉。

### 日志曾经全丢过

`import wxauto4` 会执行 `root_logger.handlers.clear()`
（见 `venv\Lib\site-packages\wxauto4\logger.py:55`），把我们的 `FileHandler` 删掉，
再塞一个只往 stderr 写的彩色 handler。于是 `bot.log` 里从此只剩 comtypes 的噪音，
出问题时完全查不了。

修法：`setup_logging()` 用 `force=True`，并且在**构造完适配器之后再调一次**
（`make_adapter()` 包了这一层）。构造后 `root.handlers` 必须是
`[StreamHandler(stdout), FileHandler(bot.log)]`，否则就是又被人抢了。

### 页面归属有个坑，构建时会自动拦下

`ui.c` 里**有两套**说法在决定一个字段显示在哪一页：

1. 字段表里第 9 个参数（`F(..., P_ADV)`）—— **从来没被读过**，是死元数据；
2. 页面数组 `pg_xxx[]` 里的 `FLD(n)` —— **这个才真正决定渲染在哪一页**。

两套写法很容易对不上：加了字段、顺手写上 `P_ADV`，但忘了（或写错了）
`pg_xxx[]` 里的 `FLD`，字段就会跑到别的页面上去 —— 而且**编译不报错、
运行也不报错**，只是设置项在界面上找不着。

这个坑真踩过：身份校验、`\agent`、截图那十几个字段全被挂进了「连续消息」页，
那一页一度有 53 项。

所以现在 `ui/build.cmd` 在编译前会先跑 `tools/check_ui.py`：检查字段有没有
挂到页面上、有没有重复挂载或越界索引、以及字段定义里的 page 参数和实际挂载
是否一致。不一致就**直接构建失败**。

```cmd
rem 注意这里用 goto 而不是嵌套的 if errorlevel ( ... ) 块 ——
rem 嵌套括号块会让 cmd.exe 在检查输出 OK 之后静默退出（exit 1，没有任何错误信息）
if not exist "%ROOT%..\venv\Scripts\python.exe" goto :skip_ui_check
"%ROOT%..\venv\Scripts\python.exe" "%ROOT%..\tools\check_ui.py"
if errorlevel 1 goto :ui_check_failed
```

界面现在分 8 页：**状态 / 群聊设置 / 消息设置 / 人设与语气 / 权限 / 指令 /
功能性API接入 / 高级**。
「权限」和「指令」分开，因为那里的开关后果最重 —— `\agent` 等于把机器交出去，
不该混在聊天设置里被顺手点开；而每条指令自己的开关和触发词单列一页，
改 `\截图` 不用先翻过 `\agent` 那一大片。

### 看一眼界面长什么样

`tools/shot_ui.py` 会启动界面、逐个页签点击（带滚动）并截图到
`data/ui_shots/`，用来确认改动真的渲染出来了，而不是「编译过了就算完」。

```cmd
venv\Scripts\python.exe tools\shot_ui.py
```

**截图必须用 `PrintWindow`，不能用 `ImageGrab` 抓屏幕。**
一开始用的是 `ImageGrab.grab(bbox=窗口矩形)`，滚动之后会抓到重绘的中间态 ——
表现为一大片空白块加几处残影，看着像界面炸了，其实界面是好的。
`PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)` 让窗口把内容自己画到我们给的
DC 上，结果稳定得多。

### 提示文案为什么会显示不全（已修）

字段的说明文字原先是这样画的：

```c
RECT hr2 = { f->rcLabel.left, f->rcLabel.top + S(21),
             f->rcLabel.right - S(14), f->rcLabel.top + S(21) + S(20) };
text_at(dc, f->hint, hr2, g_fSmall, T.text3,
        DT_LEFT | DT_TOP | DT_SINGLELINE | DT_END_ELLIPSIS | DT_NOPREFIX);
```

两个问题叠在一起：**单行 + `DT_END_ELLIPSIS`**，而且可用宽度只有标签那一列
（`S(LABEL_W)` = 344px）。于是稍长一点的说明（比如
「any = 群昵称/备注/微信昵称/微信号 任一匹配（方便，但防不了冒用）…」）
一律被省略号吃掉。

现在改成：**用和绘制同一个字体量一遍折行高度，行高按它撑开，绘制时整宽度
`DT_WORDBREAK`**。量出来的和画出来的必然一致，因为用的是同一个
`DrawText` + `DT_CALCRECT`：

```c
static int measure_hint_h(const Field *f)
{
    RECT r = { 0, 0, g_hintW, 0 };          /* g_hintW 在 layout()/paint() 里同步 */
    DrawTextW(g_measureDC, f->hint, -1, &r, DT_CALCRECT | DT_WORDBREAK | DT_NOPREFIX);
    return r.bottom - r.top;
}
```

提示自成一条整宽的带：宽字段（文本框/列表）在标签之下、控件之上；
普通字段在「标签 + 控件」那一行之下。副作用是每行高了约 24px、
页面要滚得多一点 —— 换来的是说明能看全。

### 流畅度：卡顿的根因是算法，不是显卡

界面上线后用户反馈「很卡、滚动快了出现大片空白、开关不圆、没有过渡动画」。
逐条查下来，前两条跟显卡没关系：

| 问题 | 真正的原因 |
|---|---|
| 卡 | WM_PAINT **每帧都 CreateCompatibleBitmap** 一张 1140x820 的位图（约 3.7 MB） |
| 卡 | measure_hint_h() 每帧对每个字段做 DrawText+DT_CALCRECT，而且每帧调用 **3 次** |
| 卡 | scroll_by() 每个滚轮事件都完整 layout() + 全窗口重绘 |
| 空白 | 全窗口擦除 + 重绘太慢，Windows 来不及补 |

对应的修法：

1. **提示高度缓存** —— 键是 (提示文案指针, 可用宽度)。文案一辈子不变、宽度只在
   缩放时变，所以这个缓存永远命中。每帧几千次文字测量直接归零。
2. **后台缓冲复用** —— 按窗口尺寸缓存，只有缩放才重建。
3. **内容整页预渲染** —— 可滚动区域画进一张位图，滚动只是
   BitBlt(mem, x, HEADER_H, w, viewH, cacheDC, x, g_scroll)。
   滚动路径上不再有文字测量、不再有排版、不再有分配。
4. **缓存失效用自增序号统一管** —— RENDER_DIRTY() 在改值、切页、缩放、
   状态刷新时 ++，缓存发现自己落后就重建一次。
5. **少发系统调用** —— 滚动时 SetWindowPos 只在位置真的变了才调，
   ShowWindow 也不再对全部 70 个字段无脑 Hide 一遍。

> ⚠ 这里踩过一个坑：paint_items() 一开始直接用了 layout() 算出来的
> ->rcLabel / ->rcHint。那些是**含滚动偏移的屏幕坐标**，而缓存位图是
> 「内容坐标系」，混用会让文字画错位、看起来像重影。
> 所有矩形必须按 cy 现算。

### 开关：抗锯齿和过渡动画

GDI 的 RoundRect / Ellipse **没有抗锯齿** —— 一个 28 像素的圆看着是带棱角的，
这就是「圆形不圆」。

试过 Direct2D，走不通：d2d1.h 在 C 下的 C-定义路径不成立
（D2D_USE_C_DEFINITIONS 置上了，接口结构体在编译单元里仍是不完整类型，
lpVtbl 用不了），而且它连 D2D1_RENDER_TARGET_PROPERTIES_DEFAULT 都只给 C++。
为一个小开关把整个界面改成 C++ 编译不值得。

最后用**4 倍超采样**：在 4 倍尺寸的 DIB 上用普通 GDI 画，再按 4x4 盒式降采样。
降采样本身就是盒式滤波，等于把每个像素的覆盖率算准了。
一张 52x34 的开关，4 倍也就 28k 像素，重画一次是微秒级。

过渡动画：滑块的 nim 是浮点，点击后由 15ms 的定时器按指数缓出逼近目标值
（nim += (target - anim) * 0.34），而不是从一头瞬移。

### 平滑滚动

滚轮**只改目标值**，由 16ms（约 60fps）的定时器把当前值缓动过去：

`c
g_scrollF += (g_scrollTarget - g_scrollF) * 0.30f;
`

指数缓出：离得越远走得越快，越近越慢，收尾自然 —— 不是「咔」一下跳过去。
拖动滚动条和 PageUp/PageDown 走同一套。
这一切之所以能 60fps 跑，前提正是上面那个内容缓存 —— 每帧只贴一次图。

### 保存是怎么落到文件上的

界面**不自己解析 YAML**——`config.yaml` / `persona.yaml` 里全是给人看的中文注释，
用 C 去回写基本必然把注释吃光。所以读写都交给 `ui_bridge.py`：

```
C 界面  ──写 data\_ui_in.txt（key \t 类型 \t 值）──>  ui_bridge.py apply
        <──读 data\_ui_out.txt（dump 结果）────────
                        │
                        └─ ruamel.yaml 往返读写：只改被改的那个值，
                           注释、引号、空行、缩进全部原样保留
```

已经验证：

- **全量往返零差异**——把所有字段原样写回去，两个文件与备份逐字节相同；
- **改一个值不丢注释**——改 `bot_names` 时它上面那行
  `# 机器人在群里的昵称，用于识别 @` 原样保留；
- **改坏了自动回滚**——写完后立刻用 `src.config.load_config()` 验一遍，
  不合法就把文件还原并弹窗说明（例如把 `mode` 写成别的词）；
- **保存时以界面显示为准**——直接从控件读值，不依赖 `EN_CHANGE` 通知
  （通知在跨进程写入、输入法组字时会漏，漏了就会出现「界面是新值、存下去是旧值」）。

### 自己重新编译

```powershell
cd /d C:\wechat_addon\ui

```

`build.cmd` 会自动找本机已装的 Visual Studio（通过 `vswhere`）并调用 `vcvars64.bat`，
不下载任何东西。唯一的依赖是 Visual Studio 自带的 Windows SDK 静态库
（user32 / gdi32 / dwmapi / shell32 / comctl32 / advapi32）。需要装
「使用 C++ 的桌面开发」工作负载。

想固定主题（不跟随系统明暗）：

```powershell
set WECHAT_UI_THEME=dark
ui\wechat_ui.exe
```

## 十三、人味：颜文字与「别像人机」

分两层，职责很清楚：

**第一层：`persona.yaml` 的提示词**（改完立即生效，不用重启）
约束模型的性格、语气、接梗方式，以及两个重灾区：

- **被 @ 了但没说话的时候**——必须随口应一声（「干嘛喵~」「嗯？咋啦」），
  明确禁止「在呢在呢」「我在的」「有什么可以帮你的吗」这类客服话术；
- **颜文字**——告诉模型「由程序按概率挂，你自己不要手打」，
  免得它每句都加。

**第二层：`src/style.py` 的兜底**（确定性代码，不靠模型自觉）

- `decorate()` 按 `kaomoji_rate` 掷骰子挂颜文字。
  **权重必须由代码保证**——模型对「20% 概率」的理解完全不可靠。
  实测 20000 次抽样命中率 0.200。已经在回复里带了颜文字、或者回复超过
  120 字的，跳过不挂。
- `polish()` 削掉结尾的客服腔（「有什么需要随时找我」「查天气搜资料都行」之类）；
- `fix_topic_shift()` 把**「宣布换话题」的 AI 腔**换成真人用的连接词。
  模型写过这么一句：

  ```
  诶你这梗有点脏，我不接哈。回正题——伞塞包里没，别真淋成落汤鸡喵
  ```

  这个「回正题——」一眼就是 AI：**真人换话题是直接换**，或者用「对了」
  「所以说」「哎」带一下，不会先打个报告。所以命中就替换：

  ```
  诶你这梗有点脏，我不接哈。所以说，伞塞包里没，别真淋成落汤鸡喵
  ```

  覆盖「回正题 / 回到正题 / 言归正传 / 说回正事 / 让我们回到主题 /
  回到刚才那个话题」等写法，连同后面的破折号、冒号、虚词尾巴一起吃掉。
  换完一个实词都不剩、或者后面没内容了（`回到正题。`），就只删不补，
  免得留下光秃秃的「对了，。」。persona 里也同步禁掉了这类说法。
- 空 @ 收到纯待命腔（正则 + 核心词判定，能认出「在呢在呢」「嗯嗯，我在」
  「好，有什么需要随时找我」）时，从 `nudges` 池里换一句口头话顶上，
  而「哈哈哈哈哈」「在的，我看看」这种正常回复不会被误伤。

```yaml
# persona.yaml
style:
  enabled: true
  kaomoji_rate: 0.2        # 大约每五条回复里有一条带颜文字
  strip_boilerplate: true  # 削掉客服腔
  kaomoji: [...]           # 颜文字池，随机抽一个
  nudges: [...]            # 空 @ 时的口头语池
```

颜文字池和口头语池都可以在设置界面的「人设与语气」页直接改。

## 十四、连续对话：被 @ 一次之后就不用再 @

被 @ 一次之后，那个人接着说话不用再 @ —— 但**按人分开**，两个人同时跟你说话不会串台。

### 判定是免费的

「这条算不算在跟我接着聊」**不调用模型**，用两条：

1. **明确的否决条件**（命中就关掉这个人的线程）
   - `@` 了别人
   - 提到了别的群友昵称
   - 又长（>40 字）又和上文零重合 —— 基本是在跟别人聊别的事
   - 这个话题已经聊够 `max_turns` 轮

2. **其余都算接着聊**

判定方向很关键：**默认接，只排除明确不是对机器人的**。
反过来做（默认不接、要凑够相关度才接）实测行不通 ——
「那要不要带伞」这种明显在接着问的话，和上文一个字都不重合，
按打分会判成不相关然后关掉线程，体验很差。

### 引用是唯一明确的路标

群里「右键 -> 引用」能精确指向某条消息，wxauto4 也把它拆得很干净（实测）：

```
content        = '那你说说到底带不带'      ← 回复正文（引用部分已剥离）
quote_nickname = '蓝色大肥鱼'              ← 被引用的人
quote_content  = '明天多云转阴，11到21度'   ← 被引用的原文
```

所以：

| 引用的是 | 处理 |
|---|---|
| 机器人的消息 | 一定接，窗口过期也重新接上 |
| 别人的消息 | 一定不接，直接关掉这个人的线程 |

多个人同时跟机器人聊天时，各自引用自己那条线，就互不干扰；
而如果几个人聊到了同一件事，聚合窗口会自然把它们并成**一次**回答。

### 还有第二道闸

靠启发式接上的消息（不是明确 @ 进来的），提示词里会让模型自己判断：
**明显不是在跟它说，就只回一个减号 `-`**，程序看到就不发出去。
这道闸的输出只有一两个 token，比多问一次模型便宜得多。

### 「最后一句是机器人说的」——最便宜也最强的信号

实测踩过一个坑：机器人 13:56 回完一句，群里**11 分钟没人说话**，
14:08 有人冒一句「干嘛的不回话」。没有线程（那人从没 @ 过）、没有 @，
于是被判成「没有进行中的对话」直接丢掉 —— 用户看到的就是「它不理我」。

但只要看一眼上下文就知道：**群里最后一条消息就是机器人说的**，
那下一个开口的人几乎一定是在跟它说话。这条判断不花任何 token
（历史记录本来就在手上），而且**一有别人插话就立刻失效**，不会一直黏着。

另外两个相关的修补：

- `window_seconds` 从 180 秒放宽到 600 秒 —— 3 分钟对真实聊天太短了；
- 线程落盘到 `data/threads.json`，**重启不丢**。
  之前只存内存，重启一次所有正在聊的话题就没了。

```yaml
threads:
  enabled: true
  window_seconds: 600     # 多久没说话算这个话题结束
  max_turns: 6            # 一个人最多连聊几轮就收住
  long_chars: 40          # 超过这么多字又和上文零重合 -> 判为在跟别人说
  answer_when_last: true  # 最后一句是机器人说的 -> 下一个接话的算跟它说
  dangling_window: 900    # 上面那条的时限
  persist: true           # 线程存盘，重启不丢
```

> `config.yaml` 是**启动时读一次**的。改完不重启，机器人还在用旧配置，
> 但界面上看起来已经改好了。所以程序会每分钟查一次文件时间戳，
> 发现改过就写一条警告提醒你重启。
> （`persona.yaml` / `memes.yaml` 是实时读的，改完立即生效，不用重启。）


```yaml
threads:
  enabled: true
  window_seconds: 180   # 多久没说话算这个话题结束
  max_turns: 6          # 一个人最多连聊几轮就收住
  long_chars: 40        # 超过这么多字又和上文零重合 -> 判为在跟别人说
```

## 十五、心情值：记住每个人怎么对它的

提示词里写「被怼了会回嘴」是空话 —— 模型每次都是白纸一张，记不住
「这个人刚才骂过我」。心情值把这件事变成一个**按人持久化的数字**。

### 变化不额外花调用

在同一次回复的末尾附一行标记就行：

```
哈？我说不带就不带，淋湿了怪谁喵
[mood:-6 提了下流要求]
```

程序把它解析出来、从正文里删掉、落到 SQLite。代价只有几个输出 token ——
比「先回复、再单独问一次模型这个人该扣几分」便宜得多。

### 注入格式刻意做得极短

```
正常：  [MOOD] 张三=82
偏低：  [MOOD] 张三=25（不太想搭理他，话少一点、别热情）
```

高于 `neutral`（默认 70）只注入 `名字=数值`，十几个字；掉下去才附加语气说明。
范围 1~100，默认 100（一视同仁地友好），单次最多掉 `max_down` 分，
聊得开心也能回升。

群内 `\\状态` 会列出当前心情偏低的人。

```yaml
mood:
  enabled: true         # 设置界面里也有开关
  initial: 100
  max_down: 15          # 单次最多掉多少，防止一句话打到底
  neutral: 70           # 高于这个值不注入额外说明（省 token）
  angry: 35             # 低于这个值明显变冷
```

**实测**：

| 步骤 | 结果 |
|---|---|
| 出言不逊「你个废物，问半天也没说明白」 | 回复末尾带 `[mood:-6]`，心情 100→94 |
| 同一个人再问（没 @） | 接上了，`[mood:-9]` → 85 |

## 十六、话题往低俗跑的时候

群里玩梗经常越玩越脏。比如 `ccb` 除了「踩踩背」（《豌豆笑传》鬼畜）之外，
还有一层「操操逼」的下流意思 —— 同一个缩写，看语境。

处理原则写在 `persona.yaml` 和 `memes.yaml` 里：**不翻脸、不装听不懂，
接一句然后自然把话题带开**。不展开、不追问细节、不主动加码、不配合往下写。

实测：

```
输入：母的就ccb
回复：诶你这梗有点脏，我不接哈。回正题——伞塞包里没，别真淋成落汤鸡喵
```

既接住了梗（没扫兴），又没有往下走，还顺手把话题拉回了正在聊的事。

## 十七、梗词库：认得出，还得接得住

群里一个「ccb」，模型要么当成拼写错误、要么当成正经问题去解释一遍，
两种反应都出戏。光在提示词里写一句「你要懂梗」没用——模型不知道你们群的暗号。

所以把「词 → 这个梗在表达什么情绪 → 该怎么接」写成一张表，**命中才注入**：

```yaml
# memes.yaml
memes:
  - term: ccb
    alias: [CCB, 踩踩背, 踩背, 踩背国, 大蓝象]
    note: '两层意思：①《豌豆笑传》鬼畜，大蓝象"老爷爷我给你踩背来喽"，形容荒诞抽象；
           ②"操操逼"的低俗缩写。看语境选：偏抽象就顺着玩，偏低俗就接一句
           然后自然把话题带开，别展开。'
```

内置 47 条，覆盖 2025 的热梗（丝瓜汤、技能五子棋、老登电影、馕言文、
法拉利老了还是法拉利……）和常青梗（抽象、破防、典、急了、班味……），
你点名的 `ccb` 和蒋介石梗也在里面。

**实测效果**（历史里出现过 `ccb`，然后有人问「你说 ccb 到底啥意思啊」）：

| | 回复 |
|---|---|
| 没有词库 | `ccb我也没懂，你问出题的人去` |
| 有词库 | `绷不住了，你自己先说的还来问我喵` ／ `想知道就找老爷爷踩踩背去` |

### 在群里现教

不用改文件、不用重启，用授权昵称发指令就行：

```
\\梗 add 显眼包pro | 群里最爱出风头的那个人，可以拿来调侃
\\梗 list
\\梗 del 显眼包pro
```

教进去的梗写在 `data/memes_user.yaml`，优先于内置的那份，
所以 `memes.yaml` 可以随便升级覆盖，你自己教的不会丢。

### 为什么不是每次都全量注入

只要扫历史，就很容易每轮都命中同一个词——那样等于每轮白花这笔 token，
还会把回复带偏到那个梗上。所以：

- 当前消息里命中的优先，不受限制；
- 历史里命中的最多注入 `max_history_hits` 个，且只看最近 `history_window` 条；
- 总条数和总字数都有上限。

## 十八、分段发送

微信群里没人会发一整屏文字。真人想到什么发什么，一条一句。
机器人一口气吐 200 字，比内容本身更像机器人。

拆法有优先级：

1. **模型自己留的空行**——提示词里明确说了「想分几条发就用空行隔开」，
   这是模型的分段意图，一定照办；
2. 没有空行就按句号/问号/感叹号拆；
3. 一整句逗号串到底的（比如一串天气数据），才退到逗号这一层切；
4. 按「想拆几段」反推每段目标长度再匀开，避免 54 字 + 22 字 这种一头沉。

```yaml
split:
  enabled: true
  min_chars: 50     # 短于这个长度不拆
  max_chars: 60     # 想控制在每条多少字以内（用它算该拆几段）
  max_parts: 3      # 最多拆几条
  min_part: 6       # 更短的碎片并回上一段
  delay: [1.5, 4.0] # 段与段之间的随机间隔
```

实测：

```
120 字 -> 3 段  [18] 这周北京基本晴到多云，早晚凉得狠喵。
                [78] 今天11号26/14，明天12号多云转阴21/11，……
                [24] 风力都小于3级，昼夜温差十来度，出门记得加外套。
 75 字 -> 2 段  [38] 今儿晴转多云26度，……冻人。
                [37] 周五多云，周六阴转小雨记得带伞。……
 12 字 -> 2 段  [5] 伞带上吧   [7] 外套也别忘了     ← 模型自己留的空行
```

> ⚠️ **拆出来的每一条都计入「每群每小时上限」。** 这是有意的：
> 上限卡的就是实际发出的消息条数，口径和群友看到的观感一致。

## 十九、省 token：提示词是怎么压下来的

先用 `dsh` 自己报的用量量了一遍基线，才发现问题的真实形状：

```
{"type":"status","phase":"step_end","turn":1,"step":3,
 "usage":{"inputTokens":10354,"outputTokens":188,
          "cacheReadTokens":3072,"totalTokens":13614}}
```

`step=3` 是关键——为了查天气，模型调了搜索工具，**agent 循环跑了 3 步，
每一步都把整段上下文重发一遍**。所以提示词里省下的一个字，实际要乘 3 倍花出去。

据此做了四件事：

| 改动 | 做了什么 |
|---|---|
| 分区标签英文化 | `【本群最近的聊天记录（仅供参考，不要逐条回应）】` → `[CTX]`；`【角色设定】` → `[ROLE]`。正文、人设、规则仍是中文（那些直接决定回复质量） |
| 人设瘦身 | 1486 字 → 863 字，规则一条没删，只是不再啰嗦 |
| 历史格式压缩 | `群友「张三」说：xxx` → `- 张三: xxx`；单条超 120 字截断 |
| profile 提示词瘦身 | DSH profile 里的 `personaPrefix` 和 persona.yaml 大量重复，砍掉重复部分 |

**还抓到一个大的**：给它一个「只 @ 一下、没有正文」的消息，它居然自作主张去搜天气，
一次烧掉 13090 token。加了一句「闲聊、接梗、被 @ 了就应一声，都直接回，
不要调用任何工具」之后，同一个场景回到 **2017**，省了 6.5 倍。

实测对比（同一段 30 条群聊记录，真实调用）：

| 场景 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 纯闲聊（不调工具） | 2557 | **2082** | −19% |
| 空 @ | 2554 | **2017** | −21% |
| 要查天气（调工具，3 步） | 13614 | 13034 | −4% |
| **合计** | 18725 | **17133** | **−8.5%** |

查天气那一档省得少，是因为它被 `web_search` 返回的搜索结果本身主导——
那部分不在我们手里。而日常聊天（占绝大多数）稳定省两成。

`_bench.py` 可以随时重跑这套对比。

## 二十、群内控制指令与身份校验

### 指令一览

| 指令 | 作用 |
|---|---|
| `\\stop` / `\\start` | 暂停 / 恢复（急停） |
| `\\status` / `\\状态` | 看运行状态、心情偏低的人 |
| `\\梗 add 词 \| 说明` | 教它认梗 |
| `\\agent <任务>` | **让本机 agent 干活**（默认关闭，见下一节） |
| `\\agent log` | 看最近几次 agent 调用 |
| `\\截图` | 抓一张当前屏幕发出去 |

### 身份校验：为什么不能只看群昵称

群昵称是**群成员自己就能改的**，而且全群可见。别人把昵称改成你的名字，
就拿到了控制权。微信里同一个人有好几个名字，可靠程度差很多：

| 来源 | 群里其他人看得到吗 | 自己能改吗 | 可靠程度 |
|---|---|---|---|
| 群昵称 | 看得到 | 能改 | 最弱 |
| 备注 `display_name` | **看不到**（只有机器人账号自己看得到） | 改不了 | 中 |
| 微信昵称 `nickname` | 看得到 | 能改 | 弱 |
| **微信号 `id`** | 基本看不到 | **改不了** | **最强** |

机器人账号给「大号」设的备注，群成员根本不知道字符串是什么，
所以拿它当口令比群昵称强得多。**但有个关键弱点**：冒用者只要把自己的
群昵称改成同一个字符串，微信里显示出来的发送者就也等于那个串。

实测（`identity_mode: any`，名单填微信号 `<你的微信号>`）：

```
本人（备注 <你的群昵称>）          -> True
冒用者把群昵称改成 <你的微信号>  -> True   ← 漏洞在这
```

所以真正防冒用要靠 **`identity_mode: id`**：

```
本人，读到微信号             -> True
本人，但这次读不到微信号      -> False  ← 拒绝，不退回昵称
冒用者昵称改成 <你的微信号>      -> False  ← 挡住了
```

### 身份是怎么拿到的

调用 wxauto4 消息对象的 `sender_info()`，实测返回：

```json
{ "display_name": "<你的群昵称>",                          ← 机器人账号自己设的备注
  "nickname": "望舒下清波",
  "group_nickname": "为什么美杜莎的眼睛是最漂亮的",   ← 全群看到的
  "id": "<你的微信号>",                                  ← 微信号
  "region": "瓦利斯群岛和富图纳群岛 " }
```

代价约 **400ms**（会点一下头像取资料），所以**只在指令消息上做**，
普通聊天不走这条路。结果按 `(群, 发送者)` 缓存，读到微信号后不再重复取。

它**不稳定** —— 实测有的联系人给得出 `id`，有的只给 `display_name`。
所以缓存是**合并**而不是覆盖（新结果不会抹掉之前读到的好数据），
并且有下面这条安全阀。

### 急停/恢复的安全阀

严格模式下万一 `sender_info()` 读不到微信号，主人就会被自己的规则锁在门外 ——
**机器人既停不下来也起不来**，这比被人冒用严重得多。

所以 `\\stop` / `\\start` 有一条降级通道：严格校验不过时改走宽松匹配，
并在日志里留一条 warning。要让这条阀真正兜得住，
名单里就得**同时**写上微信号和备注：

```yaml
commands:
  allowed_senders:
    - "<你的微信号>"      # 微信号：严格模式只认这个
    - "<你的群昵称>"        # 备注：急停/恢复降级匹配时用
  identity_mode: any  # any = 宽松；id = 只认微信号（推荐）
```

## 二十一、`\\agent`：把群聊变成远程操作通道

### ⚠ 先说风险

`\\agent <任务>` 走的是 `wechat-agent` 这个 DSH profile，
**文件系统、命令行、文件搜索全开着**。也就是说：

> 能在群里发这条指令的人，等于能在这台机器上读文件、改文件、跑命令。
> 中间没有任何隔离层。

默认**关闭**。开启时**强制**要求 `commands.secret` 非空 ——
否则任何把群昵称改成授权昵称的人都能操作这台机器。

### 为什么不复用 `wechat` profile

`wechat` 那份是给群里闲聊用的，**刻意关掉了文件系统和命令行**，只留联网搜索。
闲聊的机器人不该有写文件的能力。所以 agent 单开一份 profile：

```
$DSH_HOME/profiles/wechat-agent/cordis.patch.yml
```

### 权限是怎么开的

被拉起的 dsh 子进程需要 `DSH_PERMISSION_MODE=danger-full-access`。
这一个开关同时决定沙箱模式和审批策略 —— profile 里的 approval 插件是：

```js
(process.env.DSH_PERMISSION_MODE ?? 'workspace-write') === 'danger-full-access'
  ? 'never' : 'ask'
```

群里没有人能点「批准」，所以 `ask` 就等于卡死。这一步是**必须**的，
第一次实现时就是漏了它，agent 报「授权写入失败，Win32 5」「当前没有审批通道」。

### 闸门

1. `agent.enabled`，默认 false；
2. `commands.enabled` + `allowed_senders`；
3. `commands.secret` 非空且出现在指令里（对 agent 是**强制**的）；
4. 可选的 `agent.groups`（只在这些群生效）和 `agent.hours`（只在这些时段生效）；
5. 每次调用写 `data/agent_audit.jsonl`。

### 实测

```
\agent 在 C:\wechat_addon\data 下建个 _cmd_probe.txt 写上 ok，读回来确认，然后删掉

→ 收到，开始弄：在 C:\wechat_addon\data 下建个 _cmd_probe.tx
→ 已在 C:\wechat_addon\data 建 _cmd_probe.txt 写入 ok，读回确认内容为 ok，
  随后已删除（Test-Path 返回 False）。
→ （用了 write、read、pwsh，7s）
```

审计日志：

```json
{"ts": "2026-10-11 14:29:56", "group": "test", "sender": "<你的微信号>",
 "task": "在 F:\\wechat_addon\\data 下建个 _cmd_probe.txt ...",
 "ok": true, "tools": ["write", "read", "pwsh"], "steps": 4, "seconds": 7.0,
 "result": "已在 F:\\wechat_addon\\data 建 _cmd_probe.txt 写入 ok，..."}
```

## 二十三、需要管理员权限的操作：预授权通道

### 问题

机器人（和它派生的 `\agent`）跑在 **Medium 完整性**下，碰不到需要管理员的事。
而 UAC 的同意框**只能由人在电脑前点** —— 群里没人能点。

结果：agent 想去装个软件、改个系统设置，UAC 弹出来没人理，它会一直挂着，
直到 `agent.timeout_seconds`（默认 600 秒）才放弃。**群里那十分钟一片空白**，
比直接说「做不了」糟糕得多。

### 三条路，以及为什么选这条

| 方案 | 代价 |
|---|---|
| 让机器人整个以管理员启动 | agent 拿到完整管理员权限，一条错命令就能搞坏系统 |
| 让 agent 弹 UAC，你点 | 只有你在电脑前才行；不在就一直挂 |
| **预授权少数几个动作**（采用） | 你得预先批准；但爆炸半径被白名单限制住 |

### 它是怎么工作的

```
agent 写 request.json
      ↓
schtasks /run /tn WeChatElevated      ← 不弹 UAC
      ↓
%ProgramData%\WeChatElevated\run.ps1  ← 以完整管理员令牌运行
      ↓
只认白名单里的动作 → 写 result.txt
```

agent 侧只有一条命令：

```cmd
venv\Scripts\python.exe tools\elevated_request.py --list
venv\Scripts\python.exe tools\elevated_request.py whoami
venv\Scripts\python.exe tools\elevated_request.py flush-dns
venv\Scripts\python.exe tools\elevated_request.py restart-service "{\"service\":\"Spooler\"}"
```

内置三个动作：`whoami`（探活）、`flush-dns`、
`restart-service`（服务名限定在 `wuauserv` / `Spooler` / `Winmgmt` / `BITS` 之内）。

### 安全边界：ACL 是核心，不是装饰

**`run.ps1` 的 ACL 锁成仅 `Administrators` / `SYSTEM` 可写。**

这一条不能去掉。原因：

> agent 有 dsh 的 `danger-full-access`，本机大部分文件它都改得动。
> 如果 `run.ps1` 放在它改得动的地方，它就能**把自己想跑的命令写进去再触发任务**
> —— 等于直接拿到管理员权限，这个「预授权」设计完全失效。

锁上之后：非提权进程的令牌里 `Administrators` 是 **deny-only**，agent 写不进去；
而计划任务用完整管理员令牌跑，读得了。

`data\` 子目录**单独放开写入**（agent 靠它递请求）—— 那层里只有「选哪个动作」，
动作本身限定在白名单里，所以放开是安全的。

> ⚠️ **加新动作时别写成 `'run-anything' { Invoke-Expression $Args.cmd }`。**
> 那等于把管理员权限整个交出去，白名单就成了摆设。

### 安装（一次性，需要管理员）

```cmd
右键 PowerShell → 以管理员身份运行
cd C:\wechat_addon
powershell -ExecutionPolicy Bypass -File tools\setup_elevated.ps1
```

脚本会建目录、设 ACL、注册计划任务，最后**自己跑一次 `whoami` 验证通道通不通**。

### 加新动作

1. 改 `tools\elevated\run.ps1` 里的白名单 `switch`
2. **重跑一次** `tools\setup_elevated.ps1`（管理员）

第 2 步容易漏：计划任务跑的是 `%ProgramData%` 里的**副本**，不重跑就还是旧的。

### 踩过的坑

**`.ps1` 文件必须带 UTF-8 BOM。** 不带的话 Windows PowerShell 5.1 按 GBK 读中文串，
引号会被吃错位，报出「字符串缺少终止符」这种**看起来像语法错误、其实是编码问题**
的错。这个坑在 `start.ps1` 和这次的 `run.ps1` / `setup_elevated.ps1` 上各踩了一次。

## 二十四、闲聊用哪个模型：手动档位切换

一句话：**界面里选一档，下一条消息就换模型，不用重启机器人。** 不做任何自动判断
（不是「看情况挑模型」，就是你说了算）。

### 两个档位

| 档位 | 模型 | 花钱吗 | 说明 |
|---|---|---|---|
| `deepseek`（默认） | `deepseek-flash` | 按量计费 | 走 DSH 桌面账号，不用 API Key |
| `zhipu` | `glm-4.7-flash` | **免费** | 智谱开放平台，要一个 API Key |

设置界面 **高级 → 大脑 → 闲聊用哪个模型**。

`\agent` 指令**不受这个开关影响** —— 它走自己的 `wechat-agent` profile。

### 哪些会跟着换、哪些不会

| 链路 | 跟不跟档位 | 为什么 |
|---|---|---|
| 群聊回复 | **跟** | 用的是 `self.brain`，就是 `dsh.model_preset` 管的那条 |
| `\agent` | **不跟** | `AgentRunner` 自己 new 了一个 `DshConfig`，见下 |
| 梗库定时更新 | **跟** | 它复用 `self.brain`（要联网搜索才能捞梗），所以跟着走 |

`\agent` 那条是**显式钉死**的，不是碰巧：

```python
# src/agent.py
agent_dsh = DshConfig(
    command=dsh.command,
    profile=cfg.profile,          # wechat-agent
    timeout_seconds=...,
    model_preset="deepseek",      # 意思就是「不加 --patch」
)
```

这里 `model_preset="deepseek"` 读起来有点绕，它的真实含义是**「不加叠加层」**，
于是用的就是 `wechat-agent` profile 里配的 `deepseek-account` / `deepseek-flash`。

为什么要显式写：`DshConfig` 的默认值**恰好也是** `deepseek`，所以「不写」也能对 ——
但那是巧合。哪天有人改了默认值，或者顺手把整个 `cfg.dsh` 传进来，agent 就会悄悄
跟着闲聊换模型，而这条链路上跑的是**完整文件系统和命令行权限**，不该有这种意外。
`tools/test_model_preset.py` 里有三条断言钉着它（不吃叠加层、不被塞智谱的 Key、
走自己的 profile）。

### 为什么换模型不用重启，也不用复制 profile

`dsh` 支持 `--patch <文件>`：在 profile 之上再叠一层覆盖。所以：

    档位 deepseek -> 不加 --patch，就是 profile 里原来那套
    档位 zhipu    -> 加 --patch dsh\model-zhipu.yml

回切就是「不加 `--patch`」，**天然回到原样**，不存在把原配置改坏的路径。

至于「不用重启」：`brain.py` 每收到一条消息都会**新起一个 `dsh` 进程**，
profile 是那时候重新组合的。机器人每分钟检查一次 `config.yaml` 的修改时间，
发现变了就把这三个字段当场抄过来（见 `Bot._reload_model_preset`）——
所以**最多一分钟内生效**，不用重启。

只热切换这三个字段是有意的：它们只影响 `brain.py` 拼命令行，不涉及白名单、
频率、人设这些「半途换掉会出事」的东西。其余配置仍然要重启才生效。

实测记录（机器人不停机，13:04:06 改的文件）：

    13:04:52 WARNING config.yaml 改过了，但配置只在启动时读一次 —— 要生效得停一次再启动
    13:04:52 INFO    闲聊模型已切换：deepseek / profile 自带（按量计费） -> zhipu / glm-4.7-flash（免费）（下一条消息生效）

### 智谱的 Key 放哪

申请：<https://bigmodel.cn/usercenter/proj-mgmt/apikeys>
（注册 `open.bigmodel.cn` → 登录 → 创建 API Key。**目前调用 API 不强制实名认证**。）

拿到后填在设置界面的「智谱 API Key」，或者直接写 `config.yaml` 的
`dsh.zhipu_api_key`。留空则回退到环境变量 `ZAI_API_KEY`。

**密钥不会进公开仓库**：`config.yaml` 是 gitignore 的，而 `dsh\model-zhipu.yml`
里写的 `apiKeyEnv: ZAI_API_KEY` 只是一个**变量名**，真正的 Key 由 `brain.py`
按档位塞进子进程环境。

### 三个坑（都是实测踩出来的，写下来免得再踩）

**1. `--patch` 必须排在 `--json -` 前面。** dsh 的用法是
`dsh [--profile] <name> [options] [app-args...]`，`--json -` 之后的都算 app 参数，
`--patch` 放后面会报 `unknown option '--patch'`。
参数拼装的单元测试看不出这个 —— 真的跑一次 `Brain.ask()` 才炸出来。

**2. 叠加层里必须给模型声明 `reasoningEfforts`。** 不写的话，哪怕上游默认值是
`low`，也会直接报 `provider "zhipu" model "..." does not support reasoning effort "low"`。

**3. `apiKeyEnv` 的名字两边要对上。** 叠加层里写什么，`brain.py` 就得往环境里塞什么。
对不上会报 `no credential for provider route ...`，而且报错文本不会告诉你
「其实环境变量里是另一个名字」。

### 免费模型会被下线

`GLM-4.5-Flash` 在 **2026-01-30 已经下线**了，请求被自动转去 `GLM-4.7-Flash`。
所以哪天报「模型不存在」，第一件事是去看
[官方定价页](https://docs.bigmodel.cn/cn/guide/start/pricing) 上的免费模型列表，
把 `dsh\model-zhipu.yml` 里的 `glm-4.7-flash` 换成新的编码。

顺带一提，**联网搜索不跟着换**。web 工具的 `searchProvider` 仍然是
`deepseek-official`，也就是搜索那部分还是走 DeepSeek —— 换模型不会改变这一点。

### 怎么自己验（不花钱、不要 Key）

思路是**把叠加层的端点指向一个本机的假模型服务**，这样不用任何 Key 就能验证
「档位 → 参数 → 路由」整条链，还能把发出去的请求体抓下来看。

这三个文件都在 `data\`（**gitignore 的，不在仓库里**，属于本机的调试脚手架）：

| 文件 | 作用 |
|---|---|
| `data\_fake_llm.py` | 假的 OpenAI 兼容服务，把请求体写进 `_fake_llm_requests.jsonl` |
| `data\model-zhipu.yml` | 和 `dsh\model-zhipu.yml` 同结构，只把 `baseURL` 指向假服务 |
| `data\_e2e_preset.py` | 用 `preset_dir=data` 调一次真的 `Brain.ask()` |

跑法（一个窗口一个）：

    venv\Scripts\python.exe data\_fake_llm.py
    venv\Scripts\python.exe data\_e2e_preset.py

请求体会落到 `data\_fake_llm_requests.jsonl`，能看到路由确实换了，而且
`tools` 有三个（`web_search` / `web_fetch` / `exit_plan_mode`）——
这是「换了模型也还有搜索能力」的证据。

> 别人 clone 这个仓库是**没有**这三个文件的。要复现就照上表自己写一份，
> 加起来不到 120 行。

## 二十五、让 `\agent` 操作浏览器：为什么难，以及正确姿势

这一节是一次**真实事故**的复盘。用户让 `\agent` 打开学习通刷课，并在指令里
明确写了「运行完成后别把浏览器关了」—— 结果浏览器被关了两次，而且它回报
「浏览器保持打开…没有关」。

### 先纠正一个误解：`\agent` 根本没有浏览器工具

用户说「用浏览器工具」，但那个工具在 `\agent` 这条路上**不存在**：

- DSH 的运行时（`app.asar`）里，唯一带 browser 的包是
  `@deepseek-ai/dsh-client-ui-sidebar-browser`，只有 `lib/client.js` ——
  它是**交互式客户端界面**的侧边栏浏览器。
- `dsh --profile wechat-agent --dump-config` 里没有任何 browser 插件。

也就是说：`browser_snapshot` / `browser_click` 这类工具只活在**你现在正在用的
那个 GUI 会话**里；机器人跑的是一个无界面的 `dsh` 命令行进程，那里永远没有。

所以这不是配置能修的问题。agent 当时改用 Edge 的远程调试口（CDP）驱动，
**方向是对的** —— 它甚至自己写了 `tools\cdp.py`。问题出在它怎么拿到那个调试口。

### 浏览器为什么被关了两次

| 时间 | 发生了什么 |
|---|---|
| T+0s | 指令到达，里面写着「运行完成后别把浏览器关了」 |
| T+66s | 它起 Edge：`--remote-debugging-port=9222 --user-data-dir=<真实配置目录>` |
| T+78s | **`Stop-Process -Name msedge -Force`** —— 把你正在用的 Edge 全杀了 |
| T+80s | 用目录联接 `%USERPROFILE%\EdgeCDP` 重新起了一个带调试口的 Edge |
| T+326s | 它检查了一下：msedge 进程还在，标签页也在 |
| T+331s | 回报「浏览器保持打开…没有关」 |
| T+331s | **指令结束，浏览器被回收** |

第一次是它**主动杀的**，第二次是**运行环境回收的**。

**为什么它非杀不可**：`--remote-debugging-port` 只在 Edge **启动时**有效。
已经跑着的 Edge 收到新的启动请求时，只会把 URL 转交给已有进程，
**这个参数被静默忽略**。想拿到调试口，就只能先让 Edge 全退掉。

**为什么第二次一定会发生**：实测确认 —— agent 用 `Start-Process` 起的任何进程，
都会在它那条指令结束的瞬间被回收：

```
工具调用: Start-Process -FilePath cmd.exe -ArgumentList '/c','ping -n 600 127.0.0.1' -PassThru
工具返回: Id: 12300  ProcessName: cmd  HasExited: False     <- 运行期间确实活着
dsh 退出后: Get-Process -Id 12300 -> 什么都没有           <- 被回收
```

所以「让浏览器一直开着」这个要求，`\agent` **在架构上就做不到**。它当时那句
「浏览器保持打开」在它检查的那一秒是真的，几秒后就是假的。

### 正确姿势

**浏览器要由 `\agent` 之外的进程来起。** 用现成的脚本：

```
tools\edge_cdp.cmd
```

它会先检查 Edge 是不是已经在跑（在跑就直接告诉你「先关掉」，**它不会替你关**），
然后带上调试口和目录联接把 Edge 起起来。之后你再去群里让 `\agent` 操作它 ——
它挂上去就行，不需要杀任何东西。

> `tools\edge_cdp.cmd` 里的 `--user-data-dir` 指向 `%USERPROFILE%\EdgeCDP`，
> 那是一个指向真实 Edge 配置目录的**目录联接**，所以登录态和你装的油猴脚本都还在。

**安全权衡，必须知道**：这个 Edge 开着的时候，**本机任何进程**都能通过
`http://127.0.0.1:9222` 读你的页面、代你点击、以你的登录身份操作网站。
这正是它能替你刷课的原理，但它确实是**敞开的**。用完就关掉 Edge。

### 已经加进 profile 的硬约束

`wechat-agent` 的提示词里加了两条（见
`%USERPROFILE%\.dsh\profiles\wechat-agent\cordis.patch.yml`）：

1. **红线**：绝对不要关掉用户正在用的程序（浏览器、微信、explorer、游戏）；
   `Stop-Process` / `taskkill` / `CloseMainWindow` 都不行。要先关才能做的事，
   **停下来问**。汇报时必须说出对环境做了什么改动（「我重启了浏览器」），
   不许只写「任务完成」。
2. **你起的进程活不过这条指令**：做不到「留着浏览器」就直说，并给出正确做法
   （让用户先起带调试口的 Edge）。**不许**回报「浏览器保持打开」这种假成功。

### 顺带修掉的一个隐性坑

`tools\cdp.py` 依赖 `websocket-client`。写它的那次，这个包**恰好**在环境里
（大概是哪个依赖捎带装的），但它没进 `requirements.txt` —— 换台机器或者重建
venv 就会 `ModuleNotFoundError: websocket`。已经补进去了。

## 二十六、`\刷课`：为什么它必须单独一条指令，而且不能走 AI

```
\刷课              列出配好的课程
\刷课 舞台          按名字打开（Substring 匹配）
\刷课 https://…     直接打开一个网址
```

做的事只有一件：**用你自己的浏览器打开课程页**。剩下的交给油猴脚本
（它自己会解析任务点、播视频、往下一节走）。毫秒级返回，零 token。

### 课程表在设置界面里怎么填

**权限 → 课程表**：一行一门课，左边填课程名、右边填网址；点「＋ 添加一行」
多一个空行，**全空的行在焦点离开后自己消失**，不用手动删。

存储格式没变，还是 `名字 | 网址` 的字符串列表：

```yaml
brush:
  courses:
    - 舞台人生 | https://mooc2-ans.chaoxing.com/...
```

界面只是在**渲染层**把每一行拆成两个输入框，读写走的还是同一个字符串。
所以后端一行都没改，schema 也没加新的数据类型。

> 手写的对象形式照样能用（`{name: …, url: …}`），两种可以混着写。

### 同一个控件也换掉了所有「每行一个」的字段

原来是 11 个「一行一项」的文本域（白名单群、机器人昵称、授权昵称、可信会话、
颜文字池、空 @ 口头语池，以及 agent / 截图 / 开程序 / 重启 / 刷课 的触发词）。
现在**全都是同一套控件**：一项一个输入框，单列的写法就是 `parts` 只给一项。

```json
{"kind": "rows", "wire": "list", "sep": "|", "parts": ["群名"]}
```

`wire` 仍然是 `list`，所以纯前端的事 —— 加别的成对字段照抄这一行就行。

**换的时候唯一会倒退的能力是「粘贴一整列」**（文本域本来能做到）。所以
粘贴处理器会按行拆开、逐行建行；而且**往已有内容的框上粘贴不覆盖**，
插到它后面 —— 否则往一条已有记录上粘贴，那条记录会被悄悄吃掉
（这个是浏览器测试抓出来的）。

### 长列表：收起显示前 4 条

条目 **超过 4 条**的列表默认收起，但**不是整块藏起来** —— 留**前 4 条**，
让人一眼能认出这是哪个池子。底栏两个按钮：

```
[ ＋ 添加一行 ]                                  [ 展开 20 项 ▾ ]
     ↑ 左下角，常驻（收起时也在）                      ↑ 右下角
```

条目 ≤ 4 的列表本来就看全了，不收也不给按钮。收起状态下点「添加」会
**先自动展开** —— 否则新行加在看不见的地方，用户会以为没反应。

**这里有一个踩了两次的坑**：光写 `el.hidden = true` 是**藏不住的**。
`.rows-list` 和 `.rows .row` 都设了 `display: flex`，作者样式优先级高于
浏览器默认的 `[hidden] { display: none }`。第一次是 `.modal`（弹窗永远显示），
第二次就是这里（标签写着「展开 20 项」，21 行原样躺着）。

**规则**：凡是给元素设了 `display`，就顺手补一条 `[hidden] { display: none }`。
`app.css` 里这两条现在都有注释标着。

**另一个容易踩的细节**：删空行必须等焦点真的离开**整行**才能做。要是盯着
单个输入框的 `blur`，用户从「课程名」按 Tab 到「网址」时那一行会在中途被删掉。

### 为什么不让 `\agent` 干这件事

我们真的试过，而且付出了代价。结论是这条路**结构上**走不通：

| 障碍 | 说明 |
|---|---|
| agent 起的浏览器活不过指令 | 实测：`Start-Process` 起的进程会在 dsh 退出的瞬间被回收。所以「刷完别关浏览器」它根本做不到 |
| 要让它活就得有调试口 | 而 Edge 的调试口**只能在启动时加**。已经开着的 Edge 会静默忽略这个参数 |
| 于是它只能先杀再开 | 实测它跑了 `Stop-Process -Name msedge -Force` —— **在用户明确说了「别把浏览器关了」的那条指令里** |
| 为了让调试口能用，还得绕开安全限制 | Edge 在默认配置目录上拒绝开调试口，所以第一版搞了个目录联接指向真实配置。这被 Edge 当成另一个配置：油猴不运行，而且配置状态被搞坏（登录态丢失） |

所以 `\刷课` 走的是最简单的那条路：**不碰浏览器配置、不起调试口、不用 AI**。

### 和 `\开` 的区别

`\开` 走提权通道（能启动需要管理员权限的程序）；`\刷课` 什么都不需要提权，
就是让系统按 URL 关联打开一个网址 —— 用户默认用什么浏览器就还是什么浏览器，
写死 `msedge` 会把 Chrome 用户也拽到 Edge 上。

### 一次失败为什么值得单独修：429 兜底

同一个下午还遇到一条：用户发「啊啊啊」，机器人**一个字都没回**。日志：

```
15:01:08  消息到达 → 开始观察（聚合静默 6s）
15:01:31  生成失败：429: {"code":"1305","message":"该模型当前访问量过大"}
15:01:34+ 什么都没有 —— 没重试成功、没回复、消息被丢掉
```

17 秒说明 **DSH 内置的重试（默认 5 次）已经跑完了**，是那个免费模型持续过载。
免费模型被挤爆是常态，而「沉默」不是可接受的失败方式。

现在：**主模型彻底失败时，原地把档位换成 deepseek 再试一次**，成功与否都会
把档位改回去（改的是 `cfg.dsh.model_preset`，而 `Brain.cfg` 和它是同一个对象，
这条不变量有测试钉着）。

**这不是「自动挑模型」** —— 档位仍然完全由你手动决定；这里只在一次调用
彻底失败之后退一步，代价是一条群聊消息的钱（不到一分钱），换来的是不石沉大海。

### 圣遗物那几列是从哪来的

接口只给 `setId`（15001 这种）、`FIGHT_PROP_CRITICAL` 这种枚举和一堆哈希，
名字全靠查表 —— 都并进 `assets/enka_names.json` 了（同一次生成）：

| 要显示 | 从哪来 | 规模 |
|---|---|---|
| 套装名「角斗士的终幕礼」 | `store/gi/relics.json` 的 `Sets[setId].Name` -> locs | 65 套 |
| 词条名「暴击率」 | `locs.json` 里的 `FIGHT_PROP_*` **字符串键** | 52 条 |
| 武器名「星锋剑」 | `locs.json` 里的**数字键** | 444 条 |
| 部位「生之花」 | 接口给的 `EQUIP_BRACER` 等，5 个固定值，**硬编码** | 5 |

几个实测才知道的点：

- **响应里的 `setNameTextMapHash` 在本地的 locs 表里查不到**（试过，
  1212345779 返回 None）。要用 `setId` 去 `relics.json` 的 `Sets` 里再查一层。
- `reliquary.level` 是**从 1 开始**的，21 表示 +20，所以要减 1。
- `affixMap` 的值是**精炼等级 - 1**（0 -> 精1，2 -> 精3）。
- 百分比词条的值已经是百分数（3.5 表示 3.5%），不用再乘 100。
- 单件圣遗物的名字**不在** locs 里（几千件，表里只放了 501 条），
  所以圣遗物按「套装 + 部位」显示 —— 这也正是玩家的叫法。

### 缓存的是「解析后的结构」，不是渲染好的文本

`data/enka_cache.json` 里存的是把响应拆好之后的精简结构（一个 UID 约 8KB），
不是拼好的那串文字。这样**列表和「点名看某个角色」共用同一份缓存**：

```
> 查询 原神 137602053          # 打一次接口
> 查询 原神 137602053 可莉      # 不再打接口，直接重渲染
```

如果缓存的是文本，第二次点名就得多打一次接口 —— 而 Enka 的作者明确要求
别反复打同一个 UID。

### 为什么单独一条指令、不走 AI

「按 UID 查一个账号」是确定性的：一次 HTTP + 一段固定格式的文字。
走 agent 要多花一次模型调用、几十秒，而且 **agent 没法遵守这个 API 的规矩**
（见下）。和 `\开`、`\刷课` 同一个思路：确定的事不过模型。

### 这个 API 的规矩（作者写在文档里的，代码照着它做）

1. **不许枚举 UID、不许批量查。** 原文是「不要为了填数据库去大量查询」。
   所以这里没有「遍历 UID」之类的东西，只有单次查询 + 缓存。
2. **必须带自定义 User-Agent**，方便作者定位问题（写死在 `src/enka.py`）。
3. UID 端点有动态限流，打太快 429。
4. 响应里的 `ttl` = 「下次真的去问 MHY」的秒数，**这段时间要用本地缓存** ——
   反复打同一个 UID 照样吃限流。作者建议用 Redis，这里用
   `data/enka_cache.json` 代替。

对应到配置就是 `min_interval_seconds`（默认 3 秒）、`max_per_hour`（默认 60），
**两个都按真实请求记账、都落盘**，所以重启绕不过去。

### 群里的公开指令：为什么另立 `/` 前缀

群里 `\` 开头的一律要**授权 + 口令**，那是控制指令（停、重启、截图、agent）。
「查个公开的展柜」不该要口令 —— 而**群友不知道口令**，把查询塞进 `\` 体系
就得给全群发口令，等于口令公开。

所以公开指令走 `/`，并且有三道约束，**少任何一道都会变成被人刷的入口**：

| 约束 | 在哪实现的 |
|---|---|
| 必须 @ 机器人 | `Gatekeeper.public_command` |
| **只认白名单群** | `Bot.handle_public_command` 里的 `prefilter` |
| 暂停/急停期间不回复 | 同上 |

> 白名单那条特别说明一下：**控制指令那条路是故意不查白名单的**
> （主人要能从任何群把机器人停下来）。公开指令面向全群、无口令，
> **不能跟着沾这个光**，否则机器人待过的任何群都能刷它。

公开指令用**严格匹配**（第一个词等于或以指令词开头），不用
`classify_command` 的模糊匹配。那几级「包含 / 子序列」是给**授权者**打错字
用的（`\桌面截图给我` 要能认出来），而公开指令面向全群 ——
宽匹配会把 `/随便说点什么` 也变成入口。这一条有测试钉着。

### 角色名是从哪来的

接口**只返回 `avatarId` 数字**，名字要靠一张映射表。官方文档自己也说这是
「最大的挑战」。完整 store 有 1.5MB，但真正要用的只有「ID → 名字」这一列，
加起来 8KB（312 个角色），所以：

```cmd
venv\Scripts\python.exe tools\build_enka_names.py
```

它会从 `api.enka.network` 的 store 镜像（**不需要代理**）拉数据，生成
`assets/enka_names.json`。出新角色时重跑一次。

**三个游戏的字段名各不相同**，工具里都写了：

| 游戏 | avatars 里的名字字段 | 本地化表 |
|---|---|---|
| 原神 | `NameTextMapHash`（数字 hash） | `store/gi/locs.json` |
| 星穹铁道 | `AvatarName.Hash`（**字符串** hash） | `store/hsr/hsr.json` |
| 绝区零 | `Name`（**本地化 key**，不是 hash） | `store/zzz/locs.json` |

> 踩过一次：`store/` 下还有一个 `store/ef/`，键是 4/6/8 这种小整数。
> 第一版把它当成了绝区零，生成出来的名字是「弧光/余烬」——**全是错的**。
> 真正的绝区零是 `store/zzz/`（键是 1011 这种，名字对得上安比、猫又、妮可）。

### 能看到什么、看不到什么

| 看得到 | 看不到 |
|---|---|
| 昵称、等级、世界等级、成就数、深渊进度 | 背包、原石、摩拉 |
| 展柜里每个角色：等级、命座 | 抽卡记录、充值 |
| 武器：名字、等级、星级、精炼 | 没放进展柜的角色 |
| 圣遗物：套装、部位、强化等级、主词条、四个副词条 | **角色详细数据没开放时，上面三行都没有** |
| 区服 | |

最后一条是硬限制：Enka 拿的是游戏里「展柜」**公开**的那部分。
玩家自己关了展柜就查不到；只开概要（没开详细数据）时能拿到名字和等级，
拿不到命座/武器/圣遗物 —— 这时候程序会**明说**缺了什么、怎么才有，
而不是默默少显示几行让你以为坏了。

### 接口只对公开数据，但请求本身走第三方

查询会把 UID 发给 `enka.network`。展柜数据在游戏里本来就是公开的，
所以不算泄露隐私；但要知道**这台机器在访问一个第三方站点**，
和 `\agent` 那种本机操作是两回事。

### 界面上是一个可折叠的框

「功能性API接入」页按 **一个 API 一个框**组织（schema 里的 `group` 条目）：

```json
{"t": "group", "title": "米哈游账号查询（Enka.Network）", "items": [ ... ]}
```

默认**全部收起**，点标题右边的箭头展开该 API 的全部配置，**一次只开一个** ——
展开 B 的时候 A 自动收起来。理由是这类功能会越加越多（天气、翻译、
图片生成……），全铺开来一页几十个字段，找东西只能靠翻。

这一页现在是：

```
note(页面总说明，常驻)
group(米哈游账号查询（Enka.Network）, 9 个字段)
      └─ 框内小标题「频率与超时」分隔出超时/间隔/上限
group(（占位）下一个 API, 0 个字段)
      └─ 里面写了加新功能的三步
```

> **一个 API 的东西就都放在它自己的框里。** 第一版把「频率与超时」单列成
> 第二个框，其实那三项（超时、调用间隔、每小时上限）本来就是账号查询**自己**的
> 配置 —— 拆出去等于把同一个功能劈成两半，找配置得开两个框。

几个实现上的点：

- **折叠用 `max-height` 过渡**，不是 `display:none` —— 后者没法做动画。
  展开动画结束后把 `max-height` 放开成 `none`，否则框里的内容（比如
  `rows` 加了一行）变高之后会被那个固定值切掉。
- **状态是模块级的一个变量**（`openGroupKey`），不是每个框各记各的 ——
  手风琴天然是互斥的，状态必须在框之间共享。
- 切走再切回来会记得刚才开的是哪个框。

「有过渡动画」这件事是**测出来的**，不是看着像：测试在点击后的 400ms 内
按帧采样框的高度，断言存在中间态（实测 0 → 1 → 4 → 10 → 19 → 32 → 51 →
75 → 106 → … → 842，38 个中间采样点）。只断言「展开后高度 > 0」是测不出
动画的 —— `display:none` 切换也能让高度从 0 变正。
